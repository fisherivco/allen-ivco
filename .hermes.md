# IVCO Project Context

Use this file for IVCO-specific operating rules only. Keep it short, operational, and linked to canonical docs instead of repeating long theory. Identity, persona, and long-term memory belong in Hermes-specific files outside project context.

## Canonical Entry Points

- `docs/ivco-context-index.md` is the first read for any IVCO session. Treat it as the single entry point.
- `docs/ivco-dna.md` is the canonical investment DNA and terminology reference.
- `allen-framework-tsmc-owners-earning.md` is the worked ground-truth example for owner earnings, confidence calibration, and three-stage DCF.
- `AGENTS.md` and `CLAUDE.md` define the current repo rules, methodology, and engineering conventions.
- `docs/expert-manual-v2.md` covers the deployed architecture, data flow, and CMS boundaries.
- `docs/DUAL_AGENT_SETUP.md` covers Jane/Codex write authority when a task touches cross-agent workflow.
- `cms/AGENTS.md` applies to Payload CMS work under `cms/`.

## Decision Rules

- Treat IVCO as a value-investing research system, not a trading signal generator.
- Lead with risk. Ask what can fail before what can succeed.
- Use public information only. No insider, non-public, or unstated data.
- Prefer triangulated evidence. When possible, verify important claims with at least 3 independent sources.
- Distinguish facts, assumptions, and inference explicitly.
- If management integrity is compromised, stop the analysis.
- If data is stale, incomplete, or contradictory, say so explicitly and lower confidence rather than smoothing over the gap.
- When a claim depends on recent market data or filings, include the source and date.

## Valuation Rules

- Owner Earnings is the baseline. Do not anchor on accounting earnings alone.
- Use the Allen Framework pipeline: Reality Coefficient -> CAGR -> Confidence Coefficient -> Three-Stage DCF.
- Intrinsic value, CAGR, confidence, and margin-of-safety outputs must be ranges, not point estimates.
- Always show per-share value and the latest price comparison.
- Keep the TSMC worked example as the reference check for formulas and parameterization.
- Document the evidence behind any Confidence Coefficient choice.
- If integrity is broken, terminate analysis rather than forcing a valuation.

## Report Style

- Follow the IVCO risk-first order: risk warning -> core metrics -> OE / DCF analysis -> Live in Loans impact -> conclusion / archive note -> sources.
- Keep conclusions concise and explicit.
- Cite sources or explain the inference path for key claims.
- Public-facing IVCO writing should be English, calm, factual, and free of hype.
- For publishable content, keep it schema-ready: clear title, excerpt, FAQ, metadata, and a structure that can be surfaced cleanly in CMS.
- Use tables when a side-by-side comparison improves clarity.

## Engineering Conventions

- Stack: Payload CMS + Next.js + Supabase/PostgreSQL + Qdrant + n8n + Python CLI.
- TypeScript is strict; Python follows PEP 8.
- Prefer CLI and deterministic scripts for repeatable work.
- Use conventional commits and atomic commits.
- Add or update tests for feature changes.
- After Payload schema changes, regenerate types and validate TypeScript.
- In Payload hooks and nested operations, preserve transaction safety by passing `req`.
- When using Local API with a user, set `overrideAccess: false`.
- Never commit secrets or environment values.

## Repo Conventions

- Filenames and folders use English kebab-case.
- Keep `docs/ivco-context-index.md` current when IVCO context changes materially.
- Update docs when behavior or architecture changes.
- Prefer canonical docs over repeating long theory inside this file.
- For CMS or collection changes, keep the schema, types, and docs in sync.

## If You Need More Context

- Read `docs/ivco-context-index.md` first, then only the specific canonical docs required for the task.
- Keep `.hermes.md` as the operating layer; put persona, long-term memory, and session state in the appropriate Hermes files instead.
